## 用户确认原文与适用边界

### CONFIRM-01｜EC核心业务分类

> EC 的核心业务分类是：P｜维修；M｜保养；M+P｜维修 + 保养组合。这三个是 EC 当前核心业务分类。M+P虽然履约过程中可以分别引用M和P流程，但在EC业务分类中仍然保留M+P这一核心分类。

当前结论：P维修、M保养、M+P维修与保养组合，是EC核心业务分类。
边界：M+P不是仅可删除的展示标签；分别引用M/P履约，不等于组合完成条件、金额或单据关系已经确定。

### CONFIRM-02｜普通报价维修

> 普通报价维修属于 P。报价 → 客户接受 → 中单 → 进入维修履约。“普通报价维修”不是与P平级的核心业务类型，而是P内部的一种维修履约路径。

当前结论：普通报价维修是P内部先报价、接受、中单，再维修的路径。
边界：不从本项补充所有来源的任务创建方式、全部报价权限或异常规则。

### CONFIRM-03｜即时维修

> 即时维修属于 P。上门保养服务 → 师傅在现场发现维修问题 → 与客户沟通 → 客户确认 → 师傅直接维修。即时维修是P内部的一种维修路径。不要再把“即时维修”和“保养发现维修需求”理解成两条互不相关的独立业务。

当前结论：M上门保养发现维修问题，经现场沟通及客户确认直接维修，进入P即时维修。
边界：本次明确该业务背景，不补充其他即时维修来源；后补手续归口、收款及单据特例仍按原未决项核实。

### CONFIRM-04｜M→P转换

> 保养过程中发现维修需求，本质是M → P的业务转换。路径A：现场发现维修问题，师傅与客户沟通确认，直接维修，进入P即时维修。路径B：不能/不适合现场直接处理，需要报价，报价、客户接受、中单后进入P普通报价维修。“保养发现维修需求”应该作为M→P的转换关系表达，不再作为一套完整独立履约业务重复维护。

当前结论：M发现维修需求有现场直接维修、先报价中单再维修两条转P路径。
边界：不虚构现场可修的金额、材料或审批阈值；原保养本期与新P分别推进的已有说明保留（SOURCE-029第15项）。

### CONFIRM-05｜来源与取得方式

> CALL、自主询价 / 自主报价、邀请报价、标书 / Tender、客户PO直接下单、其他有事实支持的业务来源，属于业务来源 / 取得方式，而不是与P/M/M+P平级的核心业务类型。客户PO直接下单当前是否仍适用，可以继续保留“待核实”状态。标书/Tender解决的是业务如何取得；P/M/M+P解决的是最终取得什么业务以及后续如何履约。

当前结论：CALL、询价、邀请报价、Tender及PO直单属于来源／取得维度，不能与P/M/M+P混排。
边界：未指定每种来源与每种类型的全组合关系；不根据图示推断来源必定转成交业务。PO直单适用性仍待核实。

### CONFIRM-06｜CALL与客户问题处理

> “客户问题处理”不作为独立核心业务场景，它属于CALL客户服务受理与分流。CALL可能包括简单咨询 / 答疑、查询业务进度、投诉、需要进一步跟进、需要上门服务、需要报价、转入P/M等实际履约业务。具体分流规则和结束规则仍可以继续作为待确认业务规则。

当前结论：客户问题处理归CALL客户服务受理与分流，不另建核心业务类型。
边界：咨询、进度查询、投诉等可以有受理结果，但具体结束／转交规则尚未确定；不强制每个CALL进入报价或履约。

### CONFIRM-07｜工程、安装、新装

> 工程、安装、新装统一归入P｜维修。本项目当前不另外创建“工程”“安装”“新装”核心业务类型。历史资料中出现“维修/工程”“安装”“新装”等表述，保留原始事实和历史来源，但当前业务模型统一归入P。

当前结论：工程／安装／新装归P，不新增核心类型。
边界：归属明确不代表其完整操作步骤等同普通报价维修；未有完整FLOW时只引用已有资料，不创建假FLOW。

### CONFIRM-08｜CM

> CM属于P中的紧急维修。CM是属于紧急的维修，是单独的一个环节。不再将CM标记为“性质完全未知”，不与P/M/M+P平级，作为紧急维修的独立环节表达。完整入口、审批、派工、完工等规则若没有事实依据，继续保留待确认。

当前结论：CM是P中的紧急维修独立环节，归属已明确，完整规则待确认。
边界：不据此选择插单、拒单、原PM重排或审批政策；不把历史PM术语自动等同当前P或M。
