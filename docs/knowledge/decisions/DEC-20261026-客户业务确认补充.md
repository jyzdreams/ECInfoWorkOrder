## 三、Michael会后人工确认原文

本节原文保留20项，不把“已人工确认”标成客户签字批准；条目中的“本次没有确认”继续保留其未决边界。

<a id="confirm-10-26-01"></a>

### CONFIRM-10-26-01｜客户与合同关系

一个客户可以有多个合同。

一份合同只属于一个客户。

此前听记中：

“一份合约可能有两个以上客户”

属于转写/理解偏差，不进入当前业务模型。

客户名称允许重复。

业务人员实际识别业务时，核心组合为：

合同编号 + 客户名称

<a id="confirm-10-26-02"></a>

### CONFIRM-10-26-02｜合同编号

客户本次讨论的核心编号就是：

合同编号

不是另外新增一个“工程编号”“业务编号”作为新的核心对象。

合同编号是后续业务主要贯穿识别信息。

包括：

* CALL；
* 报价；
* P；
* M；
* M+P；
* 工作工单；
* MR；
* 采购；
* SR；
* 完工单；
* 后续相关业务。

注意：

合同编号是业务识别依据。

不要擅自解释为数据库唯一主键。

CALL、SR、MR、PO、报价等仍可以拥有自己的单据编号。

<a id="confirm-10-26-03"></a>

### CONFIRM-10-26-03｜政府项目编号

政府项目存在额外编号/分类选择。

当前客户最终表达包括：

ECA、ECB等。

它与EC内部合同编号不是同一个概念。

应理解为：

合同编号
+
政府项目编号/分类

具体完整枚举仍以客户实际资料为准。

<a id="confirm-10-26-04"></a>

### CONFIRM-10-26-04｜CALL选择合同

新建CALL时：

使用文本框模糊查询：

合同编号 + 客户名称

选择后带出对应客户/合同信息。

一个合同下面可以存在多个CALL。

不要把客户名称单独作为唯一识别依据。

<a id="confirm-10-26-05"></a>

### CONFIRM-10-26-05｜CALL负责人

CALL建立后选择主管作为负责人。

主管选择方式：

文本框模糊查询：主管名称（区域）

但区域只作为展示/辅助信息。

不能按区域把主管候选范围写死。

用户可以选择：

所有区域和项目的主管。

<a id="confirm-10-26-06"></a>

### CONFIRM-10-26-06｜主管处理CALL

主管收到CALL后存在三种主要处理方向：

1. 自己解决；
2. 需要报价；
3. 需要上门，由主管派师傅。

当前确认的是业务处理方向。

不要未经确认扩展成完整状态机。

<a id="confirm-10-26-07"></a>

### CONFIRM-10-26-07｜报价不是指定报价人

此前审计中：

CALL阶段指定报价人

这一理解需要纠正。

正确理解：

报价需求进入报价组公共待办。

报价组成员均可以看到。

谁接手报价：

谁负责该报价及后续报价跟进。

CALL、主管或师傅不需要提前指定具体报价人员。

<a id="confirm-10-26-08"></a>

### CONFIRM-10-26-08｜报价版本与中单

报价员接手后负责报价跟进。

报价允许多版本：

V1 → V2 → V3……

历史版本保留。

客户最终接受某一版本后：

该报价员确认中单。

最终成交版本作为后续业务依据。

<a id="confirm-10-26-09"></a>

### CONFIRM-10-26-09｜现场发现维修问题

师傅上门后发现维修问题，可以出现：

A｜即时维修

现场可以处理并取得客户同意：

直接即时维修。

后续补报价。

B｜需要报价

在Service Report中选择：

需要报价。

并填写需要报价的物件。

不需要选择具体报价人。

提交后进入：

报价组公共待办。

<a id="confirm-10-26-10"></a>

### CONFIRM-10-26-10｜现场报价信息

需要报价时，师傅至少提供：

* 货品名称；
* 型号；
* 具体位置。

支持多行。

报价人员收到后：

人工校核、选择正式报价内容及价格。

师傅提供现场需求信息，不代表师傅制作正式报价。

<a id="confirm-10-26-11"></a>

### CONFIRM-10-26-11｜报价→MR

普通报价业务：

报价
→ 客户接受
→ 中单
→ 根据最终成交报价生成1张MR。

当前确认：

一个成交报价对应1张MR。

MR下面允许产生多张采购PO。

<a id="confirm-10-26-12"></a>

### CONFIRM-10-26-12｜分阶段采购与施工

一张MR下面可以：

* 多张PO；
* 分供应商采购；
* 分阶段采购；
* 分阶段到货；
* 分阶段施工。

因此不要再把业务强制描述成：

全部材料一次到齐 → 才允许一次施工。

<a id="confirm-10-26-13"></a>

### CONFIRM-10-26-13｜现场任务基本信息

师傅执行现场工作时，主要需要看到：

* 合同编号；
* 客户名称；
* 地址；
* 联系人/电话；
* 工作内容。

其他特殊要求可以写入工作内容。

<a id="confirm-10-26-14"></a>

### CONFIRM-10-26-14｜SR适用

M保养每次上门填写一份Service Report。

正常上门检修也填写Service Report。

一次上门：

一份SR。

因此同一个M保养业务可以因为多次上门产生多份SR。

<a id="confirm-10-26-15"></a>

### CONFIRM-10-26-15｜P维修完工单

P维修施工主要使用：

完工单。

P维修可能连续多天施工。

不要求每天产生一个独立完工结果。

最终施工完成后：

提交最终完工单。

主管确认后：

P业务完成。

<a id="confirm-10-26-16"></a>

### CONFIRM-10-26-16｜工作工单关闭

师傅完成现场工作并提交对应现场资料后：

主管确认关闭本次工作工单。

对于M：

关闭一次工作工单：

≠ 整个M业务完成。

M可能有多次保养/多次上门。

每次可以独立完成。

最终仍需要整个保养业务完成，才代表：

M业务整体完成。

<a id="confirm-10-26-17"></a>

### CONFIRM-10-26-17｜M发现P

M保养过程中发现维修需求：

可以现场处理

→ P即时维修
→ 后补报价。

需要正式报价

→ SR选择需要报价
→ 填写名称/型号/位置
→ 报价公共池
→ 报价员接手
→ 客户接受
→ 中单
→ P维修。

原M继续按照M推进。

不会因为M过程中产生P，就自动变成M+P。

<a id="confirm-10-26-18"></a>

### CONFIRM-10-26-18｜M+P

M+P是EC真实存在的业务分类。

M+P：

在业务开始时就可以被定义为M+P。

不是：

M做着做着产生P以后自动变成M+P。

M+P完整结束条件等详细规则仍然保留待确认。

<a id="confirm-10-26-19"></a>

### CONFIRM-10-26-19｜车资

车资与：

师傅工作工单

关联。

SR或完工单现场可以直接填写车资。

但允许：

后续补充/修改具体车资明细。

Taxi：

必须上传收据。

其他交通方式：

本次没有确认必须上传收据。

不要扩大Taxi规则。

<a id="confirm-10-26-20"></a>

### CONFIRM-10-26-20｜业务完成与财务状态

业务完成与财务状态独立。

P业务完成：

≠ 已开票
≠ 已收款。

M业务完成：

≠ 已开票
≠ 已收款。

开票、收款单独跟踪。

不要用收款状态阻止工作工单或业务完成。

> 即时维修的“后补报价”场景，业务上已经相当于完成现场收款。

- 报价组后补报价用于补齐报价业务单据／记录，不重新等待客户接受、不重新走普通报价维修的中单逻辑、不再次触发收款。
