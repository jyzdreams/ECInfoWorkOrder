# EC 工单系统 PC 多角色业务工作台设计方案

日期：2026-11-08｜版本：人工审核草案 v1｜本轮：只读核对与方案设计

本方案尚未批准实施。本轮不修改原型、PC 其他页面、移动端、Hub、推进记录、客户 Excel、业务规则、权限或数据结构，不提交、推送、发布。上一轮主管首页是当前本地候选基线，不能当作本轮新增成果或人工审核已通过。

## 1. 当前项目位置与设计结论

项目仍在业务流程确认阶段。唯一内部记录当前焦点为 TASK-060 客户需求清单持续制作／报价样板；维修整链未通过，0 批定稿，04-12 待人工评审，C-04 阶段材料放行未决。当前 Hub 的 FLOW-MAIN、P、M、MR、Tender、财务等流程投影均为 PARTIAL，不能从页面完整程度推断业务闭环已批准。

建议把 dashboard 保留为统一首页入口，内部按现有角色选择不同的信息架构。共享导航、身份栏、视觉组件，按角色分别组织“受理队列、分派队列、报价工作清单、期限清单、现场安排、材料进度、票款清单、管理概览”。不创建首页专用业务对象、待办存储、审批或状态机。

CS、主管、报价组优先详细设计。其余角色提供布局、模块及现有入口映射。**仓库不作为本期可实现的独立 PC 角色；CR 与 BOSS 作为现有角色必须保留。** 报价接手闭环缺失、阶段供料、财务异常等问题列为依赖，不在首页工程中顺手补业务。

### 1.2 当前角色核对

| 用户所列角色 | 当前 PC 身份与页面权限 | 设计处理 |
| --- | --- | --- |
| CS 客服 | CS；dashboard、create、workorder、dispatch、srFolder、settings；导航另外隐藏 dispatch | 以现有可见 CALL／客户入口为主，不借权限表中有 dispatch 就新增客服派工快捷按钮 |
| 主管 | TL；dashboard、workorder、dispatch、srFolder、report、settings；覆盖脚本追加 maintenance | 个人办理与区域待认领分开，复用现有分派中心 |
| 报价组 | QUO；dashboard、quotations；覆盖脚本追加 maintenance | 公共需求与本人明确负责的报价分开，不按区域自动预派报价员 |
| 标书组 | TENDER；dashboard、quotations、tender | 标书期限与关联报价，不扩大成项目履约审批 |
| 师傅 | MASTER；PC 为 dashboard、srFolder；现场执行已有移动入口 | PC 做本人任务与服务记录摘要；执行仍进入现有移动工作入口，不新授 PC dispatch 权限 |
| 仓库 | PC ROLES／ROLE_PAGES 无 WAREHOUSE | 只做目标概念与职责边界；不新造角色或借采购身份登录。独立 mobile 中的 WAREHOUSE 是外部系统边界演示，不能反推 PC 已有仓库账号 |
| 采购 | PUR；dashboard、procurement、report | 以备货单 SP 及采购 PO 为实际来源；现有代码代仓务动作不等于真实岗位归属已定 |
| 财务 | FIN；dashboard、finance、report | 财务部门工作清单；个人分工缺少明确字段时不命名“我的待核对” |
| 管理员 | ADMIN；所有页面 | 全局业务分组与系统提醒；可访问不等于每条记录是管理员个人待办 |
| 用户清单未列：CR | CR；区域业务、报价本人例外，含 maintenance | 单独提供区域客户及保养协调工作台；不能合并进 CS 或主管 |
| 用户清单未列：管理层 | BOSS；所有页面 | 保留管理视图，偏业务进展和异常；不复用管理员配置重点，不因本轮省略导致回退为错误角色首页 |

以运行时最终权限为上限，首页不补写 ROLE_PAGES／角色操作授权。角色可见、对象可读、对象可操作是三层不同检查；现有页面能打开也不证明具体业务权限已经获客户确认。

## 2. 统一的信息架构与待办口径

### 2.1 四类信息必须分开

| 类别 | 成立条件 | 命名与点击 | 退出条件 |
| --- | --- | --- | --- |
| 我的待办 | 当前用户具有现有办理入口；存在明确个人责任关系；对象当前满足待处理条件 | “我的待办”，行上写真实下一动作；进入现有业务页／表单 | 原模块处理后条件不再成立；不能用首页勾选“完成”消除 |
| 团队待办 | 明确属于当前岗位／业务范围、但未分配给本人，或为现有公共需求 | “团队受理队列”“公共报价需求”“本区待认领”等 | 分派／交接／业务状态改变后退出；本轮不造接手状态 |
| 业务统计／进度 | 当前可见对象的状态分组，可能已在他人办理或等待外部 | 明示“跟踪”“部门”“业务统计”；不能把数量称为本人办理量 | 随原对象状态变化重算，不提供独立结案操作 |
| 系统提醒 | 已有 notifications 经 getUserNotifications 过滤的提醒 | 明示提醒级别与来源；跳转还需复核目标页面和对象权限 | 读消息只改已读；业务异常是否解除需重查对象，不能因已读而算处理完 |

个人归属缺失或姓名不明确时，显示“责任归属待核”，放团队／跟踪区。不能靠区域首位员工、历史操作者、通知收件人或创建人反推当前办理人。现有姓名字段仅可用于无歧义的精确匹配；同名、角色前缀、旧负责人文本不模糊归并。

### 2.2 共用页面骨架，模块位置按角色决定

1. 保留 EC 导航框架、右上用户及人员切换、通知中心。内容标题为“我的工作台”，附角色、姓名及既有区域；部门概览明确其范围。
2. 内容先给主动作及最紧急的真实工作，概览上限 3～4 项，可以是横向简洁数字条，无需每个数字包一张大卡。
3. 主区以列表／日程／业务清单承担工作；按角色决定辅助区是否在右侧、顶部或底部，不强制每页“统计＋左列表＋右快捷＋底动态”。
4. 快捷入口最多保留 3～5 个高频操作；操作有现有表单才显示按钮，只读模块写“查阅”，不写成“处理”。
5. 仅存在真实记录时展示相关动态，最多5条。低价值的动态或快捷区可省略，不能为凑齐模板制造空卡。

### 2.3 计数、优先级与刷新

- 同一待办在同一队列按业务对象＋现有编号去重；CALL、分派任务、报价、MR、SP、PO、SR／CP、发票分别标明对象，不能相加成一个不明口径的“全部工单”。合同编号＋客户名称为识别上下文，各单据原编号保留。
- 个人与团队可互斥分组时才展示合计。异常是交叉切片，不再与待办相加。M 本次服务完成不等于 M 整体完成；P/M 完成、票款状态分开。
- 只用源字段的紧急级别、未结拒单原因、有效日期／期限或既有提醒。不得新增 SLA、超期阈值、自动升级或“超时扣分”。无有效完整日期的记录不推断“今日／逾期”；显示“时间待核”，不要硬补当年。
- 相同紧急程度按原业务适用的期限排序，其次按更新时间；字段不足时采用稳定编号排序并说明，不生成精确剩余小时。
- 操作成功后重新读取现有对象并重算；失败、取消弹窗或仅打开详情不能减少待办。无权限、数据缺失与真实零条分别呈现，TBD 不能显示为 0。
- 首页初次渲染不得触发业务补编号、初始化演示数据、自动中单、MR 写入或新的定时副作用；复用读模型时避开会保存的查询函数。上一轮 getDispatchBuckets(false) 是主管只读读取的已有候选。

## 3. 三个优先角色的详细页面方案

下列布局为候选信息架构，不是已实施页面。模块编号仅为本文定位，不创建 TASK／REQ 或新业务编号。

### 3.1 CS：受理与客户交接工作台

**重点：快速建 CALL、找客户／合同、明确已交给谁。** 不能把所有活跃 CALL 当作客服本人待办。

| 页面区域 | 布局与模块 | 内容和行为 |
| --- | --- | --- |
| 顶部动作区 | 标题左、主动作右；受理入口始终明显 | 主按钮“新增 CALL”；次入口“查询客户／合同”“全部来电记录” |
| 轻量概览条 | 3项，避免大数字卡占首屏 | 本人待跟进（仅无歧义归属）、待明确受理责任（团队／归属待核）、紧急跟踪（统计）；“待客户回复”不计数 |
| 中部主区，占约70% | “我的待跟进”与“受理范围／团队待核”两个明确分区 | 显示 CALL编号、合同＋客户、问题摘要、已有优先级、当前主管／师傅、当前处理方式及最近更新；首屏以列表为主 |
| 中部辅助区，占约30% | 客户／合同查询入口、最近来电 | 通过既有客户视图查找，不在首页复制客户主档；来电区保留仅答疑／需建单／投诉和关联 CALL |
| 底部横向跟踪区 | 已交接 CALL 最近变化 | 已转主管、已请求报价等属于跟踪；不算“待我处理”，无直接操作时只查阅 |

**CS 清单**

- 我的待办候选：owner 精确等于当前姓名、未关闭／取消、没有明确有效主管、没有师傅，且没有已交报价的记录。还需排除 handlingMethod 已解决；只有现有页面可继续处理的记录才列入。这个候选解决“新建人仍留在 owner 但已交接”的误计，需人工审核其作为 CS 持续负责口径是否适用。
- 团队／归属待核：可见的 CALL 管理“待处理”且缺少明确个人接续关系的记录；不能将已有主管待审批、师傅待接单重新派给 CS。部门全域可见并不自动证明跨区团队办理权，范围待核时只作业务跟踪统计，不挂办理按钮。
- 快捷操作：新增 CALL、客户／合同视图、全部来电记录；不新增“客服分派师傅”“客服制作正式报价”。从来电记录已有“请求报价”入口发起时，保留原去重、权限和原模块处理。
- “待客户回复”没有独立可验证状态／责任字段，不从备注文字搜索、未接电话或报价中推断。设计留为 TBD，不上线空卡或零数字。
- 原 actionButtons 非 drawer 分支虽有催单／直接完成等，当前 CALL 抽屉主操作与其不同。首页不得根据旧函数存在就额外暴露这些按钮。

### 3.2 主管：任务办理与团队调度工作台

**重点：先决定／分派，再核对完工；已分派任务是团队进度。** 上一轮三卡与左右结构可作视觉资源参考，但本方案要修正个人、团队、跟踪混算，不能直接宣布已符合新范围。

| 页面区域 | 布局与模块 | 内容和行为 |
| --- | --- | --- |
| 顶部 | 身份及范围；右侧“进入分派中心” | 明确当前主管及区域，不扩大全区权限 |
| 第一层 | 3项紧凑概览 | 我的待处理、本区待认领、相关异常；“进行中”移入调度区统计，不算办理项 |
| 第二层主体，占约65% | “我的待办”，按下一动作分组 | 待完工核对、待审批、待分派；编号、合同／客户、材料背景、师傅、可执行动作 |
| 第二层辅助，占约35% | 团队调度＋快捷入口 | 已分派任务、负责师傅、既有排程；快捷安排分派、完工核对、进度、服务记录 |
| 第三层横向区 | 本区待认领和异常分栏，按真实有无收缩 | 未指定有效主管的本区任务独立展示；已有其他主管的任务不能混入。相关最近操作可放调度区下方，不要求固定大底卡 |

**主管清单**

- 个人待办：getDispatchBuckets(false) 内 tl 为当前主管且处于待分派、待审批、待完工确认；直接分派任务按同一既有范围处理，不漏无 CALL 来源。
- 本区待认领：复用 getDispatchBuckets 的区域与 isValidSupervisorName 条件，但独立标为团队／待认领。当前没有已核实的独立“认领”按钮，行操作为查看现有分派处理界面，不新增认领写入。
- 完工核对：待完工确认队列包含“可确认”与“欠资料待补”，不能把整桶都标成可一键确认；按钮严格依 canConfirmCurrentReport。当前 CP 路径要求指定主管及完整提交字段；其他资料路径按既有函数。财务收款不是该队列的退出条件。
- 已分派且由师傅办理的记录放“团队执行中”，不列为主管本人待做；如有既有重新分派／补充备注入口，由原页面处理。
- 异常：未结任务中已存在的紧急、拒单及无法完成记录／提醒；拒单历史不能自动判定当前仍阻塞，需同时核对当前分派状态。材料提醒只显示已有状态，C-04 仍未决，不能在首页新加“主管放行施工”。
- 现有 dispatch 的 pendingCompletion 页签文字为“已確認”，而对象状态为“待完工確認”；首页用“待完工核对”，跳转保留现有页签，标签统一列入后续审核项，本轮不改源页。

### 3.3 报价组：公共需求与个人版本工作台

**重点：公共需求放在公共区，实际负责的版本工作放在个人区。** 不把地区报价员自动当接手人，不把部门所有报价视为当前用户待办。

| 页面区域 | 布局与模块 | 内容和行为 |
| --- | --- | --- |
| 顶部 | 标题、当前报价员；右侧“新增报价”“进入报价管理” | 沿用当前业务入口；不新增“接手”按钮冒充现成功能 |
| 左侧窄工作栏，约30% | 公共报价需求／未明确责任 | 只显示有来源证据的 CALL／SR 待报价记录、原单号、客户／合同、需求摘要、现有负责人；不把自主或 Tender 来源默认纳入公共池 |
| 右侧主要工作区，约70% | 本人负责报价清单 | 主视图是版本、金额、客户、下一动作；细分“待制作／修订中／终态归档”，保留原状态显示与历史 |
| 主区顶部轻量概览 | 最多3项 | 公共待报价、本人待报价、本人修订中；没有可靠个人责任时显示归属待核，不能以部门总数填个人数字 |
| 主区底部或详情辅助区 | 版本与跟进动态 | 取 quotation.history 的真实操作记录；只读成交版本、MR／备货摘要，不能把采购工作变为报价本人任务 |

**报价组清单**

- 公共候选：可读报价、待报价、owner 为空，且 source／sourceTicketId／sourceCallId／sourceSrNo 等能证实为 CALL／SR 请求。识别不完整的旧记录放“来源／归属待核”，不自动扩成全来源公共池。
- 本人候选：owner 无歧义精确匹配当前姓名且为待报价或修订中对应的原始状态。preparedBy／requestedBy 不替代当前负责人。**owner 只能证明当前记录标注负责人，不能证明已经按业务完成接手**，此差异在方案和页面说明中保留。
- 当前展示字典把报价中／需修订统一显示为“修订中”，旧“等待客户确认”迁移成报价中。首期不同时生成“制作中、待修订、等待客户接受”三套可相加数字；跟进是同一报价的上下文，不增加业务状态。
- 已有“报价／修订”入口 openQuotationEditDrawer 在报价中会按区域改 owner，与接手负责规则冲突。首页默认进入报价管理只读详情；对受影响记录不新增直接编辑快捷按钮。要做到完整公共接手与个人办理，须先有独立批准的报价整改范围，不能把改归属包装成首页路由。
- “客户已接受待中单”没有独立可靠状态；目前 confirmWon 一次提交接受资料并中单，不能凭未中单就造一条已接受待办。中单只进入现有表单；实际负责报价员核验缺失列为依赖，不增加首页的一键中单。
- 即时维修后补 isSupplementary 可作为现有只读标签，但补报价记录的专门操作尚未闭环；禁止把这类记录导入普通接受／中单／再次收款快捷路径。
- 快捷操作保留新增报价、查看待报价、查看修订中、查阅版本历史；只有原页面允许时才显示相应按钮。公共区“接手报价”、专门“后补报价办理”均暂列 TBD，不生成可点击占位按钮。

### 7.1 共用视觉规范

沿用 ec-brand.css：品牌蓝 #2990d0、主操作蓝 #1e78b1、导航深蓝 #122d45、浅蓝 #edf6fc、琥珀 #fbb000、正文 #20364a。使用当前 Arial／PingFang HK／PingFang TC／Microsoft JhengHei 字体栈。已有暗色主题变量继续适配，不用新色盘区分部门身份。

- 页面标题24～26px，区块标题16～17px，正文13～14px，辅助文字12px；真实工作信息不能缩成仅靠悬浮才能读的微字。
- 主容器以平面列表及必要边框划分，表面圆角沿用6px、控件沿用5px；复用既有图标和状态标签，不增加每区块大图标／装饰渐变。

- 1440／1280为主要PC评审宽度，1024检查折叠与列宽；减少次要列／辅助区下移，不借PC调整修改mobile目录。
- 列表加载、无任务、无权限、源记录缺失、TBD、失败重试分别呈现。原型没有异步请求的模块不加虚假加载动画／刷新时间。
- 有键盘焦点、明确按钮名、状态文字及足够对比；高频动作进入原表单后执行原校验，不提供首页批量关闭或假完成按钮。

### 9.1 允许的后续技术边界

- 统一首页路由仍是 dashboard；按state.role和currentPerson读取对应布局，未实施角色走原renderer回退。可抽取仅用于首页的只读查询／UI组件，但不重构其他业务页面。
- 首页新增选择器只派生当前对象，不持久化一份待办列表，不新增localStorage业务键，不改原对象字段。为正确入口设置现有页签、筛选和选择ID属于UI适配，不是增加业务状态。
- 先setPage／hasPagePermission确认目标页，再使用原详情／表单；不能因现有某些document级处理器能调用就绕过页权。无法无改动复用时列入该批依赖，不复制一套业务处理函数到首页。
- 已批准角色的PC登录落点可调整为已有dashboard；在首页使用现有角色＋人员切换时同步布局、数据、动作和范围，并清除旧首页筛选／详情。非首页切换保持原行为，点击首页查看，不为工作台重写其他页面导航。若要让任何页面切角色都强制回首页，另作明确交互审核。
- 报价归属、接受／中单、MR／SP／PO流转、库存、SR／CP选择、票款登记及独立mobile存储都不在首页最小范围。用户后续批准解决依赖时单列差异和验证，不能夹带进首页改版。
- 原型本地已有未提交内容保留；不覆盖整份文件、不拷贝历史版本替代当前目录，不自动Git提交、推送或发布。

### 9.2 每个角色的验证与人工审核清单

1. **口径检查**：每个指标能追溯到本方案映射行、源对象及计数；个人、团队、统计、提醒分开；跨区、无归属、同名、终态与后补异常例子均有预期结果。
2. **入口检查**：逐个点击编号、主按钮、更多、快捷操作、动态；确认到原对象与正确页签／详情；没有list别名死链、越权跨页、只读详情冒充办理或假的接手／回标按钮。
3. **办理检查**：在隔离原型样例上，从原表单完成已有操作后正确退出／移动队列；取消、失败、欠件、材料门槛、仅已读时不误减数量；不重复中单／建MR／收款。没有依赖能力的场景明确未通过，不用静态截图代替。
4. **角色切换检查**：在同一首页连续切CS→TL→QUO及同角色另一员工，检查布局、归属、范围、筛选和详情无残留；未实施角色仍能打开旧首页及原模块。
5. **视觉检查**：1440、1280、1024完整截图；默认、空态、紧急／异常及主办理入口截图；检查密度、长编号／长客户、列宽、键盘焦点与暗色主题。
6. **隔离检查**：对比本轮开始的原型其余页面、mobile、Hub、客户表等文件和关键页面结果；首页查询不改业务存储。既有错误独立记录，不声称回归全绿。
7. **人工停点**：交付源文件准确范围、完整截图、用例结果、已知限制和下一动作；用户确认当前角色后才能排下一角色。页面确认仍不是客户业务签批或整链UAT。
