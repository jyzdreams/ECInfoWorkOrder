# EC 工单系统文件写入规则

> 2026-10-15补充：[正式版与工作副本规范](FORMAL-VERSION-WORKFLOW.md)确定main是唯一正式维护版。下文三个入口/唯一维护源均指正式main；同事工作分支里的同路径文件仅为候选输入，不得直接写回正式版。保护同时覆盖底层知识、脚本与治理文件。

更新时间：2026-10-12。本规则采用用户批准的目录方案并补充GitHub提交边界，替代此前根目录文件规则的路径约定。

## 一、优先级

用户当前明确指令 → .specify/memory/constitution.md项目宪法 → AGENTS.md执行规则 → 本规则 → 具体分析/历史文档。
历史资料可作为证据，不因文件名“最新”“最终”或原型已有页面而变成当前批准范围。

## 二、三个日常入口

- 推进：根README指定内部Excel主台账，范围、任务、责任、阻塞、客户确认和验收只在这一维护源收口。
- 原型：prototype/index.html及配套代码，其他原型仅历史对比。
- 知识：project-hub/index.html。底层文档维护在docs/knowledge/；Hub是来源可追溯的查看入口，不另维护一套事实或任务进度。
- 客户确认表是按编号/版本导出的交付材料，反馈复核回填主台账。
- 目录整理不等于Excel升级、业务规则整合、需求批准或原型验收。

## 三、目录职责

| 位置 | 允许存放 | 边界 |
| --- | --- | --- |
| docs/knowledge/ | 来源索引、规则、流程、决定、需求关联、待确认项 | 重要结论追溯原件；保留编号、出处和冲突，不重复造PRD/任务板 |
| docs/analysis/ | 专题分析、方案草案、流程参考、Demo说明和配套资源 | 整理/推测不直接当批准 |
| docs/audit/ | 定版前审计与对应证据 | 保留版本结论；整改进度回到Excel |
| docs/review/ | 评审、整改计划/结果、回归和验收记录及配套证据 | 旧PASS只证明对应版本，不替代客户业务验收 |
| docs/governance/ | 文件规则、目录说明、知识同步和搬移记录 | 治理信息不写成业务决定 |
| docs/history/ | 旧PRD、流程、设计、演示、交接等整理文档 | 历史不等于全部无效；被替代的规则保留依据 |
| materials/ | 客户原始资料、纸样、参考附件和inbox | 新客户资料先放inbox，登记后归类；保留原名原内容，同名文件按收件日期分目录 |
| outputs/<批次>/ | 内部指定推进Excel及客户Excel、DOCX、PDF、图片等交付材料 | 原有批次保留；新交付独立批次；中间检查/预览/inspect文件放.codex，不覆盖旧交付 |
| prototype/ | 当前原型代码与简短使用说明 | 修改需需求/决定和验收场景；不混入会议/表格/报告 |
| project-hub/ | 知识中心页面、样式、生成数据与简短说明 | 独立分析/评审报告放docs；机器数据不人工另写业务事实 |
| project-hub/scripts/ | Hub必要生成脚本、路径映射 | 可随项目版本管理的唯一维护源；.codex旧入口只兼容转发 |
| knowledge-base/ | 历史知识界面和原始机器快照、简短说明 | 只追溯；不另作为当前知识入口 |
| archive/、backups/ | 历史原型和完整快照 | 原位置只读，不拆分快照中的代码/文档 |
| store/ | 临时收件 | 不是唯一业务依据或交付源 |
| .codex/ | 解析、构建、预览、验证和技术路径映射 | 中间产物不当客户交付物；映射不是项目进度 |
| .agents/、.specify/、.github/ | Agent、规格工具、CI配置 | 必要配置原位置保留；正式开发前不恢复旧规格目录 |

根目录仅保留README.md入口、AGENTS.md执行指引和必要配置。应用目录可保留简短README，详细业务整理文档统一放docs。客户原件和交付文件按用户选择继续保留materials/、outputs/。

## 四、写入和更新顺序

1. 从README选当前维护源，判断文件身份，检查同名文件与版本。
2. 新业务信息先核对客户原件，再维护docs/knowledge/中的规则/决定/来源。
3. 在指定Excel记录需求/任务/依赖/确认与验收，不新增平行Markdown或JSON进度表。
4. 对明确任务修改原型；客户版按稳定编号/版本导出，反馈复核回填。
5. 知识需要Hub展示时用project-hub/scripts/build-v2.js生成并核对；先用--check-paths做只读检查。目录维护仅修路径，不触发业务内容重建。旧build.js已禁用。
6. 输出后验证文件、链接、资源、编号和状态；记录未整合资料与未决项。

## 五、搬移与历史记录

搬移前列原路径/目标路径/引用并查重；原件、交付批次和完整快照不顺手搬移。
搬移后核对哈希，链接修复单独记录。冻结审计/历史证据中的原路径保留，以搬移记录追溯现址。
Hub已有FILE、SOURCE、FACT、DEC、FLOW、REQ、PAGE编号不因改路径重编；技术映射唯一维护源为project-hub/scripts/path-migrations.json。
未来文件按本规则归类，不恢复旧路径或用复制文件掩盖链接失效。

## 六、命名和状态

文件名体现用途；交付批次、日期或稳定编号体现版本，避免final-final、最新版等不稳定命名。
正式需求状态：草案、评审中、待确认、已批准、已废弃。有明确批准依据才标已批准；页面存在、已生成、已打开不等于批准或验收。

当前没有有效开发plan.md。进入正式开发后按获批准范围和项目宪法建立spec/plan/tasks，不因历史提示恢复旧specs/。

多人同时工作遵循[团队协作规范](TEAM-COLLABORATION.md)：每批约定写入人，主台账统一回填，共享原型/Hub文件统一整合，不覆盖他人的未提交修改。

GitHub提交遵循[GITHUB-SUBMISSION-RULES.md](GITHUB-SUBMISSION-RULES.md)：本地过程文件保留但忽略，正式报告/引用证据及共享工具随项目保存；.github/仅放配置。不要用宽泛文件类型或整份审计目录忽略正式业务资料。
