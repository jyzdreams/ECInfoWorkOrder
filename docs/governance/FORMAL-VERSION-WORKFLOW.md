# EC 正式维护版与同事工作副本

生效：2026-10-15，依据用户批准的版本管理计划。适用于所有同事及其AI，不限Codex。
本规则替代旧规范中“各批次另指定正式文件写入人”“main改原型自动发布”的约定；其他目录、事实和验收规则继续有效。

## 1. 哪份是正式版

| 身份 | 位置与权限 | 边界 |
| --- | --- | --- |
| 正式维护版 | GitHub `main`；只有用户账号 `jyzdreams` 及用户授权、使用该账号的AI可更新 | 用户日常使用的唯一基线，不等于客户已批准或验收通过 |
| 同事工作副本 | 每人独立克隆、独立工作分支，如 `work/<人员>/<批次>` | 可修改和验证；没有正式台账或正式定稿身份 |
| 用户AI整合候选 | `codex/<整合批次>` | 审查、整合和回归后由用户授权账号更新main；未提交修改是本地候选，必须在汇报中说明 |

不在同一目录复制“正式/范本”两套入口。每个分支使用相同路径：

- 推进表：`outputs/2026-10-12-finalization-prep-v1/EC工单系统项目推进总表-v2.xlsx`。
- 原型：`prototype/`。
- 知识入口：`project-hub/index.html`；底层资料：`docs/knowledge/`。

保护覆盖整个main，包括来源、知识、Hub生成脚本、规范、CI和交付资料。同事可以编辑自己副本中的文件，但不能直接推送、合并或删除正式分支。不得共用用户GitHub凭据，也不共用可写的正式工作目录。

## 2. 同事及其AI开工

1. 先读根README、AGENTS及本规范，再读文件/协作/提交规则；任何AI均须遵守。
2. 从当前 `origin/main` 建立自己的工作分支，记录基线提交、批次、关联编号和负责文件；已有未提交工作先保存，不使用reset/clean覆盖。
3. 只在工作分支修改，客户原件保留；Excel修改是回填建议，不能宣称已更新正式主表。
4. 本地验证后推送工作分支，可开PR到main供审查，不自行合并、不触发正式发布。
5. 提交下面的交接信息。旧工作分支可以继续保存成果，但同步前必须与当时的正式main重新比较。

```text
工作分支与基线提交 / 本次提交：
业务批次 / 需求、决定、问题编号：
变更文件 / 修改前后行为或规则 / 原因与事实依据：
Excel涉及工作表、稳定编号、字段、旧值、新值：
实际验证场景、结果、证据 / 未验证项：
客户确认、原型修改、业务验收各自状态：
未解决事项 / 下一动作：
```

## 3. 我们怎样决定同步

先取固定提交并只读比较，不自动pull、merge、cherry-pick或覆盖正式文件。审查必须同时看共同基线→同事版本、共同基线→正式版本，识别同名文件和业务规则的双方改动；不能只看提交标题或文件数量。

AI按业务分组给用户看：

| 编号与FLOW | 同事改了什么（前→后） | 依据 | 正式版已有变化/冲突 | 影响页面、状态、权限 | 验证 | 建议 |
| --- | --- | --- | --- | --- | --- | --- |
| 原编号 | 具体变化 | 来源/无依据/待确认 | 具体冲突或无 | 具体影响 | 已验证/未验证 | 采用/暂缓/不采用 |

用户逐组确认后才能同步；“看看差异”“更新远端信息”和页面存在均不算采用授权。用户批准的是当时明确列出的提交和内容，后续提交须重新审查。没有用户决定的部分保持未采用，不因技术可合并就带入main。

每批差异和用户采用依据放 `docs/review/<日期-同步批次>/`，保存基线、同事提交、正式提交、采用/暂缓/不采用范围及证据；它是评审记录，不是另一套任务总表。实际任务状态仍回填原Excel。

## 4. 正式同步规则

- **原型**：逐项整合获准内容，保护既有整改；检查正常/异常路径、权限、材料门槛、CP/SR等受影响场景。
- **Excel**：以正式主表为底稿，按既有REQ/TASK/UAT等编号及字段回填。新增/删除工作表、公式、链接或编号也须列明；不接受二进制自动合并、整份替换或按行号盲写。
- **知识与Hub**：先核事实/决定/冲突及原编号，再更新获准底层资料；必要时由用户授权AI生成Hub。不得直接覆盖同事整套JSON/内嵌模型，也不手工创建第二份事实或进度。
- **冲突**：双方改变同一字段、流程、权限、状态或批准结论时，列明差异交用户判断；不使用“远端更新所以覆盖”或“保留本地所以忽略”作为业务依据。
- 同步前保存正式基线及未提交成果；验证后建立可追溯提交。回退通过对应提交的反向变更完成，不force-push、不重写共享历史。
- 用户本人及其AI日常整理无需重复批准每个技术步骤；同事内容进入正式版仍必须有明确采用决定。客户批准与UAT只凭真实证据更新。

## 5. GitHub实际保护与发布

- main更新规则仅允许账号 `jyzdreams` 绕过；其他账号保留工作分支写入权限。
- 独立历史规则禁止main删除及非快进推送；不把CODEOWNERS或文字说明当作权限保护。
- Pages仅 `workflow_dispatch` 手动触发；工作流同时校验正式仓库、`main`、触发账号和重新运行账号均为 `jyzdreams`。
- `github-pages` 环境仅允许main分支部署，由 `jyzdreams` 审批；不允许管理员绕过环境保护。推送、合并与审查均不自动发布。
- 授权AI不得主动发布，除非用户明确要求该次发布。可读仓库不代表能修改正式版；各人自己的本地副本不受GitHub写入保护。

具体生效设置、保存点和验证边界见本次 `docs/review/2026-10-15-version-management/` 实施记录。新增管理员、绕过账号、规则变动需由用户决定并重新检查权限；不向同事共享管理员Token。

## 6. 本次边界

本次交付：完整成果保存、正式基线、分支和发布保护、共同规范、一次隔离差异演练。
后续：按业务批次审查同事改动、继续内部走查和三入口内容对齐。
待确认：真正的客户业务未决项保持原状态；本次不替客户作决定。
明确不做：不新增第二套主表、不整改业务交互、不自动发布、不把17组局部回归升级为整链或客户验收。
