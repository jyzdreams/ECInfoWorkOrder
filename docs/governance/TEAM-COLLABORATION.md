## 1. 开始工作先看三个入口

先打开[根README](../../README.md)，从它指定的文件开始，不按“最新”“最终”等文件名猜版本。

| 入口 | 管什么 | 维护原则 |
| --- | --- | --- |
| 指定推进Excel | 需求、任务、责任、依赖、阻塞、客户确认、验收 | 唯一内部主台账；不建立第二套进度表 |
| prototype/ | 当前原型 | 修改必须关联已有需求/决定/问题编号和验收场景 |
| project-hub/ | 业务全景、流程、需求和来源追溯 | 底层资料在docs/knowledge/，页面和机器数据按核对结果生成 |

旧PRD、历史原型、旧PASS和机器覆盖率供追溯，不能替代当前客户批准、业务验收或项目进度。10/12资料准备已接入最新要求并升级推进表；当前范围和全链验收未完成，维护源以根README为准。

## 2. 文件放哪里

| 文件类型 | 位置 | 规则 |
| --- | --- | --- |
| 新客户附件、听记、照片 | materials/inbox/，登记后归入materials对应类别 | 原名原内容；同名文件按收件日期分目录，先登记再归类 |
| 业务整理、分析、审计、评审、治理、历史说明 | docs六类目录 | 具体职责见[目录说明](PROJECT-STRUCTURE.md)；不在根目录或应用目录散放报告 |
| 内部主台账、客户Excel/DOCX/PDF和交付图 | outputs/<日期-用途-版本>/ | 新交付独立批次；旧批次保留，不覆盖、不按旧索引自动选对外版本 |
| 中间检查、inspect.ndjson、预览、调试、解析缓存 | .codex/verification/<批次>/或对应工具目录 | 不发客户，不提交Git，不混进新outputs批次 |
| 正式审计/验收证据 | docs/audit/或docs/review/<批次>/ | 保留版本、场景和结果；与临时检查产物区分 |
| Hub必要构建脚本和路径映射 | project-hub/scripts/ | 随项目版本管理，只有这一份维护源 |

现有outputs中的99-检查记录和inspect文件保持原位，作为历史检查资料；上述分流规则用于后续产物。store/只供用户临时放文件，不另做客户收件入口。

## 3. 多人同时工作怎么避免覆盖

1. **按业务批次分工**：开始前约定业务流程、现有需求/问题编号、负责文件、写入人和验收条件，记录到现有推进表；姓名和时间不清楚时不得编造。
2. **推进Excel统一回填**：正式主台账仅由用户及其授权AI回填。其他同事提供对应编号的结论/证据，由维护人核对回填；不各自改一份主表，不用Git自动合并Excel。
3. **同一工作文件一人主写**（仅用于同事各自工作分支；正式版写入资格仍按2026-10-15规则）：不同文件可并行；prototype/index.html等共享大文件即使涉及不同页面，也先指定一个整合人。其他同事提供独立分支改动或评审意见，由整合人合并验证，不覆盖他人未提交修改。
4. **知识按所属文件维护**：规则变化更新docs/knowledge/对应来源/决定/详情，保留原编号；历史结论保留，新结论记录出处、适用范围及替代关系。新问题保持待确认，不以原型已有按钮证明需求获批。
5. **正式Hub仅由用户授权AI按批次生成**：先审查并接入用户采用的底层资料，再生成和检查。不得多人同时覆盖data/*.json或index.html，不人工另写事实与批准状态。

评审意见可放docs/review/<批次>/并关联现有编号，它是输入和证据，不是第二套任务总表。任务状态、责任和阻塞最终回填推进Excel。

## 4. 每批推进和客户确认

每批先核对原件并梳理需求/流程，按角色实际走查当前原型，记录断点和未执行场景。已明确部分由团队整改并内部复测，准备候选范围、完整解释和可演示的主路径后，再请客户集中确认范围及真正未决项；按客户决定补齐相关交互，开展业务验收并记录冻结版本。

2026-10-12用户纠正：资料归档和局部页面检查完成，不代表需求/原型已走通。当前先执行主台账TASK-039～041内部准备，不把“找客户定稿”列为眼前第一项。确实只能由客户提供的政策、样张和人员信息可提前澄清；技术断点与资料可判断的问题由团队先处理。候选方案保持待确认，不能擅自填业务答案或因此提前关闭审计/UAT。

分别记录三项：**客户确认、原型修改、业务验收**。任一完成不能代替其余两项。

客户版由主台账按编号/版本输出；客户可以填写确认和意见，团队复核后回填主台账。保存确认人、日期、对应版本、确认范围和原始依据，不只写“客户说可以”。

已明确依据的内部问题由团队处理，不全部丢给客户；缺少依据、存在冲突或改变范围的内容不得自行定版。新增意见在冻结后登记变更，记录影响和是否需重新确认。

## 5. Hub更新与检查

必要环境：Node.js、Git，完整项目目录及根README指定资料。脚本仅使用Node内置模块，没有额外npm安装要求。从项目根目录执行：

```sh
node project-hub/scripts/build-v2.js --check-paths
```

上面只检查路径和编号，不写文件。只有已核对知识需要进入Hub时，由本批生成负责人执行：

```sh
node project-hub/scripts/build-v2.js
```

第二条会更新Hub数据和内嵌页面。执行后核对来源路径、编号、业务状态、栏目显示和关联详情，按实际变化保留生成文件差异；不得把目录整理当成业务重建。旧build.js已停用，.codex里的build-v2入口仅为兼容转发。

## 6. 提交与交接

提交前查看差异，只提交自己负责且验证过的变更；保留其他同事的修改。不要提交缓存、登录信息、锁文件和中间检查文件。首次交接要同步完整目录搬移和必要脚本，不能只复制规范或README。

提交范围遵循[GitHub提交规范](GITHUB-SUBMISSION-RULES.md)：本地备份、审计提取缓存和临时检查不提交；正式报告及其引用证据保留。被跟踪的过程文件需停止跟踪，单独写入.gitignore不会自动移除。正式Pages只允许用户在main手动触发并审批；工作分支推送、PR和正式合并均不自动发布。

每批结束用以下内容交接，不另建立进度台账：

```text
业务流程 / 需求或问题编号：
修改文件 / 分支或版本：
事实或决定依据：
客户确认状态 / 原型修改状态 / 业务验收状态：
验证场景、结果与证据位置：
未解决问题 / 下一责任人和动作：
```

当前待团队按批次指定主台账维护人、原型整合人及Hub生成负责人，本规范不替团队填写实际人名。10/11目录治理批次仅处理收件、工具、产物分流和协作规则；10/12经用户授权完成最新要求核对、Excel升级和Hub同步。原型整改、客户范围批准和业务验收仍待后续批次，不能沿用目录治理批次的完成结论。

2026-10-13用户明确授权当前AI（Codex）作为项目经理推进，由其负责本轮任务拆分、主台账回填、知识/Hub同步、内部走查和原型整合；用户只确认准备好的范围、候选及评审节点，不承担拆任务或逐份维护资料。真实客户签批、业务评审人及客户联络人仍按实际记录，不由AI代签或虚构。其他同事接手仍先约定负责文件，不能同时覆盖本轮维护源。

2026-10-13后续确认方式：用户已确认“先内部走通，再找客户定稿”，不重复请求批准该顺序。每次只引导一个小问题，先给具体例子/画面、说明需要确认什么和判断标准，再提供清楚的选项；不把整份技术报告或多个业务决定合在一个确认框里。技术修复正确性由AI验证，用户可确认成果表达及客户核实问句；用户看懂/认可问句不等于已选择业务规则、客户批准或UAT签收。

2026-10-13随后纠正，作为当前提问规则：**先问用户实际业务，不只确认问句表达；用户也无法回答的问题，记录后再集中问客户。** AI先查已有依据、一次用一个具体例子问用户；保留用户回答的身份、原话、日期、适用范围及与原件的冲突。用户说明可用于内部核对，但不冒充客户正式批准。只有用户明确不清楚或复核后仍无法确定的部分进入客户待确认清单，不因用户尚未回复就认定无法回答，也不自行联系客户。技术问题由AI处理，等待业务回复时继续不依赖该答案的内部工作。

## 7. 每轮让用户看见实际进展（2026-10-12用户确定）

所有协作AI每次对话结束都在最终回复中固定汇报以下三项，比较本轮开始与结束的实际变化。只讨论、答疑或更新规范的对话也保留三项；无变化明确写出，并简要说明原因。

2026-10-14用户再次强调：每个回复必须让用户看见当前整体推进位置，不能只报本轮文件变化。最终回复先用简明清单或表格显示：当前阶段/批次、已走通部分（注明局部或整链）、未完成/阻塞部分、下一步及执行人；随后保留下方三入口的本轮变化。讨论或答疑时也显示当前进度，不等用户追问。中间更新说明正在做的节点和下一项检查即可。整体状态从已有主表/证据读取，历史成果标为当前基线，不算本轮新增，不另建台账或编造完成百分比。

| 项目 | 本轮变化 | 完成状态与下一步 |
| --- | --- | --- |
| 推进表 | 新增/修改的需求、任务、确认或验收编号；状态如何变化；可点击的当前主表 | 完成了什么，哪些仍待客户/团队处理，下一个动作 |
| 原型 | 修改的页面与交互、关联需求编号；未修改则写“本轮无变化” | 已实现与已验证分开，列关键未通过或未执行场景，下一批改什么 |
| 知识库 | 新核对的来源、规则、决定或待确认项；底层资料与Hub是否同步 | 已核对、待确认和冲突分开，指出待补依据或下一步 |

表后用一句话说明当前批次是否完成、项目停在哪一步，以及下一责任人的具体动作。有真实阻塞时解释原因；没有业务变化不编造进度或百分比。

历史成果仅标为“当前基线/保持上轮”，不重复计作本轮新增。资料整理完成不等于客户已确认，代码已改不等于业务验收通过，页面存在不等于业务已覆盖；客户批准和验收结果必须有对应证据。

这三项是对话交接格式，不新建Markdown/JSON进度台账。任务进度仍只维护根README指定Excel；不为凑齐汇报修改表格状态、复制交付文件或重建Hub。实际文件更新时提供对应入口/证据链接，用户不必逐份翻辅助材料才能判断进展。
