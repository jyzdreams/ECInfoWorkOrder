## 更新顺序

1. 用户授权AI更新内部工作记录；业务结论先核原件/用户说明，更新对应知识的原编号与替代边界。
2. 先执行 `node project-hub/scripts/build-v2.js --check-paths`，再按已核对内容执行同脚本生成Hub。生成模型只作查看，不人工另记进度。
3. 需要客户版时，使用工作区依赖运行 `project-hub/scripts/export-client-workbook.mjs`，从同一记录生成。AI先读取表格技能，通过依赖工具确定Node和包目录；调用时以 `EC_WORKSPACE_NODE_MODULES` 指向该工具返回的Node包目录。预览/检查用 `EC_PREVIEW_DIR` 指向 `.codex/verification/<批次>/`，不放交付目录。
4. 同批次里程碑编号、需求确认、原型准备、验收状态在Hub与客户表一致。导出日期/版本明确；未定排期留空，不编造完成日期。
5. 客户填写后保留回收原件，按C/B等编号复核，将实际答复、身份、日期及依据回填内部记录/知识，再导出新版本。生成器发现已有回复或客户意见会拒绝覆盖；不得清空回复以绕过保护。
6. 内部技术验证、用户可用性审查、客户业务确认和业务UAT分别记录。无新证据不关闭旧阻塞，不以状态数量或机器关联率算完成度。

## 协作与共享

### 首页与日常汇报用语（2026-10-19用户反馈）

用户已反馈首页能看懂，但术语过于AI化。首页和日常汇报直接写“做什么、谁来做、怎样算完成”，例如用“核对”代替“对齐”、“部分功能检查”代替“局部回归”、“定稿”代替“冻结”、“接下来谁处理”代替“下一责任人”。CALL、MR、SR、CP等真实业务名称和原编号保留；详细任务、原始依据和历史状态也保留，不通过改文字改变业务结论。用户对首页文字的反馈，不计作客户业务确认或业务验收。

本分工只替换旧“所有任务只维护在内部Excel”的约定，其余正式版保护继续有效。内部记录、客户导出工具、治理及Hub受main保护；同事仍在独立工作分支提交候选，用户逐组采用后才同步。客户表里的意见也是输入，不直接替换正式结论。

不增加日常入口、不创建并行工作板、不提交缓存或临时预览。本批不自动提交、推送或发布，不改变一期范围或客户验收。
