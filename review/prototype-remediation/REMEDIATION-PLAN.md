# EC 工单系统 Prototype 业务一致性整改计划

- 计划日期：2026-09-27
- 状态：**待人工确认；仅供后续整改排期，不代表已经批准实施**。
- 范围：将 [全量业务一致性审查](../prototype-knowledge-audit/PROTOTYPE-KNOWLEDGE-AUDIT.md) 的全部 P0/P1，以及关键 WRONG、MISSING、INCOMPLETE，转换为可执行、可验收的原型整改项。本轮只创建本计划，未修改 Prototype、代码、Mock Data、PRD 或 Decision，未执行整改或回归测试。
- 当前原型：`prototype/index.html`、`prototype/ui-upgrade.css`；业务数据由原型内的默认数据及浏览器 localStorage 提供。页面编号沿用审查报告。

## 1. 依据、优先级与决策边界

1. **当前业务依据**：[DEC-20260927-真实业务流程讨论](../../knowledge/decisions/DEC-20260927-真实业务流程讨论.md) 的 CONFIRMED-001～017；PENDING-001/002 和 REJECTED-001 按原状态保留。此前资料与该 Decision 冲突时，本计划只按最新已确认流程确定整改方向，不改写旧资料。
2. **审查依据**：[PROTOTYPE-KNOWLEDGE-AUDIT.md](../prototype-knowledge-audit/PROTOTYPE-KNOWLEDGE-AUDIT.md) 的 P0-01、P1-01～10、SCENE-01～07、P2-03 和 KNOW-01～07。
3. **辅助事实源**：[2026-09-19 最新需求材料](../../materials/raw/ec-workorder/12-requirements-latest-20260919.md) F006～012、F027～033、F040～056、F057～062、F078；[冲突清单](../../knowledge-base/CONFLICTS_AND_UNCONFIRMED.md)、[开放问题](../../knowledge-base/OPEN_QUESTIONS.md)、[业务流程草案](../../docs/2026-09-26-business-flow-atlas-draft.md)、[项目宪法](../../.specify/memory/constitution.md)。2026-09-19 材料和 2026-09-26 草案是辅助资料，**不是客户批准的最终 PRD**；客户确认表的功能、流程、字段及权限仍待确认。
4. **处理建议含义**：`MODIFY` 是依据 CONFIRMED Decision 可进入下一轮原型设计的修改；`PENDING` 是业务问题未决，本计划只列决策门槛；`BLOCKED` 是虽有目标但缺必需外部条件，确认前不能落实；`NO-CHANGE` 表示核对后保留现状。本计划未授权执行任何建议。
5. **原型核对修正**：源码已有 `saveQuotationEdit`/`createQuotationRevision` 修订逻辑、SR 表单的“需要报价”及自动建报价、部分中单状态更新路径的自动建 SP、单次/重复排程，以及 Tender 中标后“沿用报价或询问创建报价”。审查报告记录的是其可见/可达表现。因此下列方案以**接通、区分和补全已有路径**为主，不把“界面未看见”写成“源码完全不存在”。
6. **不可越过的边界**：SP（备货单）不是 MR（材料申请单）；会计账单周期不是保养服务周期；既有工单 `待確認` 表示师傅接单，`待審批` 表示申请接单审批，不得复用为 CR/TL 完工确认；Tender 中标不当然等于客户已接受最终报价。状态显示名称、仓储数据主系统、正式权限矩阵、CP/SR 单据映射等未决细节须先确认。

## 2. 逐项整改计划

以下 15 项为本计划的统计口径。每项均按当前可见/源码行为描述；`PENDING` 项只有决策准备，不是确定修改任务。页面编号可回查审查报告第 3 节。

### R-01｜施工报告提交后由 CR/TL 确认完工（P0）

| 字段 | 内容 |
|---|---|
| Audit ID | P0-01；SCENE-01/02/03/04/06；KNOW-01 |
| 当前问题 | 师傅提交 SR 或完工单 CP 后，工单立即成为 `已完成`，跳过业务确认人。 |
| 业务依据 / Decision | CONFIRMED-010；CM 同样适用 CONFIRMED-015。旧资料 RULE-013/Q-004 冲突由最新 Decision 确定本轮判断。 |
| 当前 Prototype 行为 | `performAction` 的 SR 提交更新 `status: 已完成`；CP 提交也直接更新 `已完成`；完成通知随即发出。另有 CS“直接完成”入口，适用场景未明确。 |
| 正确业务要求 | 现场服务、客户确认/签名、师傅提交 SR 后，CR 或主管作简单确认，才正式完工；提交与正式完工必须分开记录。CP 是否必需及何时归档仍需确认。 |
| 具体修改方案 | 在师傅提交动作中保存报告及客户凭证，转入“报告已提交、待 CR/TL 确认”的**逻辑节点**，向对应 CR/TL 生成待办；在 CALL 详情或报告管理增加确认入口、确认人/时间/意见与流转记录；确认后才标记 `已完成` 并触发完成类通知/统计。已报价工单不能因 CP 路由而缺少 SR 提交证据；CP 可暂作附属单据，其准确适用条件列入待决事项。检查 CS 直接完成入口，仅在经确认的非现场服务场景保留，不得绕过本项现场服务链。 |
| 涉及页面 | PAGE-003/006/008/023～027/040；CALL 详情、移动端 SR/CP、报告管理、CR/TL 待办。 |
| 是否新增页面 | 不新增独立顶层页面；新增“待完工确认”队列视图和确认面板。 |
| 涉及角色 | MASTER、CR、TL；CS 接收最终完成通知。 |
| 影响业务场景 | 普通维修、保养、现场即时维修、CM、Tender 转入施工。 |
| 对其他流程的影响 | 报价任务若由 SR 触发，必须在报告提交后可追踪；会计开票/收款保持独立；统计和报告归档须以实际确认时间区分“已提交/已完工”。 |
| 修改风险 | 高。会影响现有 `已完成` 筛选、师傅任务列表、消息、历史样例；`待確認` 已用于师傅接单，不能复用。CP/SR 映射及客户未签名例外仍需单独确认。 |
| 验收标准 | 现场服务样例中，师傅提交后 CALL 不显示已完工且 CR/TL 有待办；CR/TL 确认前完成通知/计数不触发；确认后才显示完成并记录确认人/时间；已有 `待確認` 接单含义不变；发票收款不随工单完成自动结清。 |
| 处理建议 | **MODIFY**；具体状态文案和 CP/SR 选择规则先过决策门槛。 |

### R-02｜建立可追踪 CALL 工作队列与报价移交入口（P1）

| 字段 | 内容 |
|---|---|
| Audit ID | P1-01；SCENE-01；CONFIRMED-009 核对项 |
| 当前问题 | “CALL 管理”主视图实际为客户清单，CALL 创建藏于客户详情，缺独立生命周期队列；CS 向 CR/TL 移交报价需求的路径不清。 |

| 正确业务要求 | CS/CR 可以从可发现入口记录及追踪 CALL；CS 发起报价任务时经过 CR/TL，CR 可直接发起；CALL 与客户主档分别可查。 |
| 具体修改方案 | 将现有客户清单明确为客户主档视图，新增 CALL 列表/工作队列，复用现有新建表单与客户历史；列表按状态、类型、客户、区域、负责人筛选，并链接详情、分派、报告和关联报价。增加“请求报价”动作，记录来源 CALL、发起人、CR/TL 接收及转交 QUO 的节点；CR 直接报价也记录来源。保留现有电话答疑/无需建单分支，不把所有 callLog 强制转施工工单。 |

| 涉及角色 | CS、CR、TL、QUO。 |
| 影响业务场景 | 普通报价维修、现场即时维修、投诉或咨询转单。 |
| 对其他流程的影响 | CALL 来源可追到报价、MR、排程、SR；不能仅凭创建 CALL 自动跳过客户报价确认。 |
| 修改风险 | 中。两套现有建单入口、callLog 与 ticket 可能重复；角色可见范围仍待批准，不能据此锁定最终权限。 |
| 验收标准 | 不进入客户详情也能找到 CALL 列表、新建及筛选；客户历史可反向进入同一 CALL；CS 报价需求可见 CR/TL 接收与 QUO 任务，CR 直接发起可追来源；咨询类记录不会被误当已派工。 |

### R-03｜统一“客户接受最终报价→QUO 中单→自动 MR”触发（P1）

| 字段 | 内容 |
|---|---|
| Audit ID | P1-02；SCENE-01；KNOW-02 |
| 当前问题 | 一个中单入口把采购启动做成可选勾选，且不生成 MR；另一状态更新入口虽自动建 SP，仍未建立 MR 和接受最终版本的门槛。 |
| 业务依据 / Decision | CONFIRMED-003/006/007/008；辅助材料 F041/044/051 仅作原型现状参考。 |
| 当前 Prototype 行为 | `markQuotationWon` 写 `已中單`，未勾“同时启动采购”时无备货对象；`startProcurement` 只改采购状态；`updateQuotationStatus` 的另一中单路径会自动建 SP；`saveDataToLocalStorage` 还删除旧 `ecinfo_mr_requisitions`。报价版本材料与 MR 无持久关联。 |
| 正确业务要求 | 客户接受明确的最终报价版本，且 QUO 确认中单后，系统根据该成交版本的材料行生成唯一 MR；报价草稿/已发送/待客户确认时不生成。MR 是材料申请单，不能以 SP 或 PO 代称。 |
| 具体修改方案 | 把两处“中单”操作统一到同一业务入口；展示客户接受凭据/时间、最终版本号及 QUO 确认；提交时锁定成交版本材料快照并创建 MR 头/行，关联 quote ID、版本、客户、CALL/Tender 来源。移除“是否启动采购”作为 MR 创建条件；保留 SP/PO 为后续备货/采购实体，建立 MR→SP/PO 的显式关联，并给无材料行的报价显示“无材料申请”及原因，不能伪造空 MR。为重复点击、已有中单和修订后再中单定义幂等提示。 |
| 涉及页面 | PAGE-029～034/039；报价列表/详情/中单弹窗、备货视图。 |
| 是否新增页面 | 不新增顶层页面；需新增 MR 详情视图，见 R-04。 |
| 涉及角色 | QUO、CR/TL、PUR、TENDER；FIN 只接独立财务通知。 |
| 影响业务场景 | 普通 P 报价、M+P 的 P 支线、Tender 报价中单。 |
| 对其他流程的影响 | MR 成为备货、缺料采购、材料就绪、正式预约及施工的上游；版本号也是财务关联报价的依据，但不使财务状态跟随工单。 |
| 修改风险 | 高。现有已中单样例有缺 SP/缺类别；Tender 中标直接把关联报价标记已中单的路径可能绕过客户接受门槛，需与 R-10 联动处理。 |
| 验收标准 | 未接受或非 QUO 中单不得产生 MR；同一成交版本重复中单只保留一份 MR；MR 材料行逐项等于成交报价材料快照；未勾旧采购选项也会生成 MR；SP/PO 编号与 MR 编号不混淆。 |
| 处理建议 | **MODIFY**。 |

|---|---|
| Audit ID | P1-03；SCENE-01；KNOW-02 |
| 当前问题 | 仓管只看 SP/PO，无法看到成交报价产生的 MR、逐行备货及短缺。 |

| 涉及角色 | PUR、CR、TL、QUO。 |
| 影响业务场景 | P、M+P 的 P 支线、Tender 中标后的 P 支线。 |
| 对其他流程的影响 | 备货就绪才可推动正式客户预约；MR 与现有 SP/PO、排程和施工材料来源需要一致关联。 |

### R-06｜预排与正式客户施工预约分离（P1）

| 字段 | 内容 |
|---|---|
| Audit ID | P1-04；SCENE-01；KNOW-02 |
| 当前问题 | 师傅排程、预计施工时间和客户正式确认时间混用；材料就绪后缺 CR/TL 预约动作。 |
| 业务依据 / Decision | CONFIRMED-004/005。 |
| 当前 Prototype 行为 | CALL/标书可安排师傅、日期、重复周期，并可分派；`scheduleDate` 既没有“预计/正式”语义，也不以材料就绪作为正式预约门槛。 |
| 正确业务要求 | 中单后可先记预排师傅和预计时间；材料准备完成后，CR/TL 与客户确认正式施工时间。正式时间不等于预排时间。 |
| 具体修改方案 | 在 CALL/项目排程中区分“预排师傅及预计时间”和“客户确认的正式施工时间”，记录确认人/时间/客户回执；MR/备货就绪时生成 CR/TL 待办；正式预约动作须显示材料状态并阻止把未就绪预排误写为已确认。正式时间变化留痕。现有重复排程只在相应业务计划场景使用，不能代替正式客户预约。 |
| 涉及页面 | PAGE-003/006/028/039，CALL 详情、分派/排程弹窗、备货详情。 |
| 是否新增页面 | 不新增顶层页面；需在现有详情增加双时间区及正式预约面板。 |
| 涉及角色 | CR、TL、PUR、MASTER。 |
| 影响业务场景 | P、M+P 的 P 支线、Tender P 项目。 |
